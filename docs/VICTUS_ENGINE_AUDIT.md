**Inspected:** 2026-11-19  
**Repository:** https://github.com/FAHTHIZ/VICTUS  
**Inspected main commit:** `31457931542d52c0572970139d161a73428c21bd`  
**Purpose:** Tell the game agent what the engine already contains and what must be proven or built. This is a source/documentation audit, not a claim that every feature has been compiled or exercised on the target phone.

> Always re-check the live VICTUS main branch before implementation. The SHA above is a reproducible historical baseline; it may have moved.

## 1. Engine identity and project model

VICTUS is an independent C++20 game engine. The inspected tree contains an engine, editor, player, CLI, tests, benchmarks, Android Gradle project, sample games and extensive documentation. The project should use VICTUS as a normal external engine dependency/workspace. Do not vendor a second copy into this game repository.

The engine's documented foundations include:
- SDL3 platform abstraction and SDL_GPU render hardware interface.
- ECS, versioned scene serialization, prefabs and project assets.
- C++ runtime modules and Luau game scripting.
- A standalone player and `victus export` packaging workflow.
- Android arm64 APK build path.
- Asset import/cook/cache with stable UUID sidecars.
- CTest tests, sample projects, profiling and capture/compare tools.

## 2. Existing character models — confirmed

VICTUS contains two original model assets generated by `tools/characters/build_vanguard.py`:

| Asset | `victus_vanguard_01.glb` | `victus_vanguard_02.glb` |
| Model style | Broader shoulders, angular two-piece chest, squared crown, one rear fin | Narrower/tapered armor, continuous chest shell, softer crown, paired side/rear details |
| Highest-detail mesh | 20,632 triangles | 20,588 triangles |

| Materials | Four shared family slots | Four shared family slots |

| Scale | About 1.70 m authored | About 1.70 m authored |

The robot identity is a dark visor with two cyan-white eye indicators, a small chest status window, V insignia, pearl ceramic armor, graphite structure and restrained emissive accents. It has no human face. Do not describe it as a human character or assign human facial morph targets to it.

Shared documented animation clips:
- Idle (4.0 s, loop)
- Walk (0.8 s, loop)
- Run (0.55 s, loop)
- Jump (0.6 s, one-shot)
- Fall (0.8 s, loop)
- Land (0.4 s, one-shot)
- Interact (0.9 s, one-shot)

Shared controller: `vanguard_locomotion.vanim`, with speed blend and grounded/jump/interact transitions. Named child nodes provide `Socket.Head`, `Socket.Hand.L`, `Socket.Hand.R`, `Socket.Back` and `Socket.Root`. These are named child nodes, not a formal socket component.

**Game decision:** use V-01 for the final VICTUS dummy reveal behind a chair. It is a harmless prop-like character in an ordinary pose; the humour comes from the contrast with the facility's build-up. V-02 can be a secondary background/facility character if it helps the story.

## 3. Rendering — present in code, not yet proven on this phone

The inspected status and limitation documents describe these 3D capabilities:
- HDR forward clustered PBR with metallic/roughness materials, normal/emissive maps and alpha cutout.
- Directional cascaded shadows and local point/spot-light shadows.
- SSAO, image-based lighting, sky and physically based atmosphere.
- Reflection probes and irradiance volumes.
- Bloom, exposure, tone mapping and color grading.
- FXAA, TAA, motion vectors, temporal upscaling and dynamic resolution.
- Mesh LOD, occlusion culling, GPU instancing, decals and fog.
- Low/Medium/High/Ultra quality tiers.
- CPU and GPU particle systems (subject to documented restrictions).
- Water and environment features.

Important limitations for this project:
- All audited GPU evidence was produced on Mesa lavapipe software Vulkan or CI's virtualized Apple GPU. No physical Android GPU had been tested.
- SDL_GPU in this version does not expose GPU timestamp queries. Per-pass GPU execution time is unavailable; CPU timings and render-path explanations exist.
- Volumetric fog requires Medium quality or above, has a bounded froxel grid and has no volumetric self-shadowing. It is not guaranteed to be affordable on the Hot 10S.
- Foliage is instanced, but culling/LOD selection is CPU-side per instance; no persistent GPU instance buffers, impostors or built-in foliage wind are documented.
- LOD transitions use hysteresis, but no cross-fade/geomorph is documented.
- Do not assume area lights, dynamic global illumination, clouds, weather, depth of field or motion blur exist.
- Use local lights selectively. More light objects do not automatically mean a better-looking scene.

**Implementation direction:** prove the base forest with high-quality composition, materials, a small number of important shadow-casting lights and modest fog first. Add higher-cost features only after measuring. Avoid making the whole image depend on expensive volumetric fog or post-processing.

## 4. Physics and character movement

The engine includes:
- Jolt 3D physics and Box2D 2D physics behind VICTUS-owned components.
- Rigid bodies, colliders, triggers, collision filters, forces, impulses, raycasts and overlaps.
- 3D CharacterController using Jolt CharacterVirtual with slope handling, step-up, ground adhesion, air control, jump and moving-platform velocity.
- Joints and articulated ragdolls (kinematic, powered and passive configurations).
- Terrain heightfield collision and mesh/convex colliders.

A critical limitation in the audited baseline: ragdolls do **not** provide automatic get-up or root/capsule follow. Do not enable ragdoll on the player and assume the controller will reconnect itself. A proper recovery flow must coordinate:
1. Temporarily suspend or constrain ordinary movement while the fall is active.
2. Preserve the gameplay root/capsule as the authoritative movement object.
3. Drive a safe, authored recovery animation/pose.
4. Restore normal controller/animation state only when the character is stable and grounded.
5. Avoid collider penetration, root teleport and sudden velocity changes.
6. Test on slopes, uneven terrain, stairs and near walls.

For ordinary trips, a procedural stumble animation or short controlled physical reaction may be cheaper and more stable than a full ragdoll. Use ragdoll only for deliberately authored showcase moments after profiling.

Source: [VICTUS Known Limitations](https://github.com/FAHTHIZ/VICTUS/blob/main/docs/KNOWN_LIMITATIONS.md) and `engine/physics`.

## 5. Animation and faces

The audited engine supports:
- glTF skeletal animation and GPU skinning.
- Animation clips, cross-fades and `.vanim` state machines with blend spaces.
- Controller layers, node masks, IK constraints (two-bone, FABRIK chain, look-at).
- Bone-name retargeting.
- glTF morph-target weights and animation.

Known trade-offs:
- Morph-target deformation is currently applied on the CPU for each animated entity and uploads a modified vertex copy when weights change.
- Tangent deltas and per-vertex motion vectors for deformations are not handled in the documented path.
- Morph targets are skipped by retargeting.
- Detailed facial animation is therefore appropriate for a small number of close-up speaking hero characters, not a crowd of many animated faces.
- There is no automatic humanoid pose correction in retargeting, no foot-contact IK and no bone-map editor.

**Recommended use:** put most dialogue delivery into body/head/eye/eyelid motion and use a small, tested set of facial morphs for the one or two characters shown close-up. Keep the robot Vanguard models as robots.

Sources: [VICTUS Animation](https://github.com/FAHTHIZ/VICTUS/blob/main/docs/ANIMATION.md), `engine/animation`, `engine/assets/src/importers.cpp`.

## 6. Audio and dialogue

The engine uses miniaudio and documents:
- WAV, Ogg Vorbis, MP3 and FLAC audio assets.
- AudioSource and AudioListener components.
- Master, Music, SFX, UI, Ambient and Voice buses.
- 3D spatialization and distance attenuation.
- Streaming, looping, one-shots, voice limits and priority/virtual voice handling.
- Per-bus low-pass and a simple shared comb-filter reverb send.

Audio gaps include no HRTF, no convolution reverb, no per-source effects or audio profiler. Android playback has not been listened to on physical hardware in the audited baseline.

**Important separation:** VICTUS provides audio playback/mixing. It does not by itself provide natural TTS or dialogue creation. Generate or record the finite set of dialogue lines separately, check all voice/model rights, package the finished audio as normal VICTUS audio assets, and test playback on the device.

## 7. AI, navigation and NPCs

The audited engine includes Recast/Detour navigation, NavMeshSurface/NavAgent, path finding, crowd agents, and behavior-tree AI with selectors, sequences, waits, cooldowns, timeouts, blackboards, sight/perception and hearing/noise concepts.

Limitations include single-tile navmesh, synchronous builds and no visual behavior-tree editor. Keep the first stage's NPC count small. Use simple state machines and behavior-tree nodes already supported. Do not create a complicated crowd system for a short mobile demo.

## 8. UI and input — biggest immediate mobile gap

The engine has retained game UI components for canvas, rectangles, panels, images, text, buttons, layout and scroll. The UI can draw over 2D/3D scenes and can be driven by Luau. It has keyboard navigation support.

The Android guide explicitly documents:
- Touch events are accessible through touch-to-mouse and the script APIs `input.touch_count()` and `input.touch(i)`.
- The UI can use tap-to-click behavior.
- **There are no built-in virtual sticks or on-screen gameplay buttons yet.**
- Touch is not recorded in the current deterministic regression captures.

Game-level work required:
- Virtual movement stick.
- Camera-look touch surface.
- Contextual interaction button.
- Field-tool button.
- Pause/settings overlay.
- Multitouch pointer identity and ownership.
- Prevent movement/camera from continuing while a modal UI is active.
- Gamepad mode and automatic touch-control visibility changes.
- Testing for simultaneous touches, touch cancellation, app pause/resume and screen rotation.

Do not add a joystick-looking static image that does not actually control the character. Controls must be fully functional.

## 9. Android export — build path exists, device validation does not

The audited docs describe Android arm64, Android 9/API 28+, Vulkan 1.1, SDLActivity, SDL3, the VICTUS player and a `game.vpak` payload. The app is configured for `sensorLandscape` by default. The Android APK build is integrated with Gradle and CMake.

Documented mobile settings:
- `rendering.mobile_quality` (default Medium).
- `rendering.mobile_target_fps` (default 30).
- Dynamic resolution.
- ASTC mobile texture compression (BC7+ASTC 4x4 for `auto`; BC1+ASTC 6x6 for `small`).
- Touch querying through Luau.
- Lifecycle pause/resume handling.

Important:
- The engine requires Vulkan 1.1 for Android; no OpenGL ES fallback is documented.
- Only arm64-v8a is built in the audited configuration.
- No Android phone or emulator had been installed/run in the audited platform matrix.
- No thermal or real Android memory profiling had been performed.
- No Android Game Mode / Performance Hint integration was documented.
- A successful APK build is not proof of Hot 10S compatibility.

Read [VICTUS Android guide](https://github.com/FAHTHIZ/VICTUS/blob/main/docs/ANDROID.md) and [Platform Support](https://github.com/FAHTHIZ/VICTUS/blob/main/docs/PLATFORM_SUPPORT.md) again before building.

## 10. Asset workflow

The engine supports glTF 2.0 / GLB import, PBR materials, skeletal animation, morph targets, LOD simplification via meshoptimizer, stable metadata sidecars, cooked asset cache and ASTC texture compression for mobile.

Use this standard route:
1. Author or acquire the source asset with verified rights.
2. Import through the regular asset database and record metadata.
3. Check materials, normals, scale, skeleton, clips, texture sizes and LOD.
4. Run project validation and export.
5. Test the packaged asset in the actual player.
6. Record performance and memory impact.

Do not bypass VICTUS's importer for convenience, or create hidden asset-specific renderer paths. Current glTF parser security advisories are documented in VICTUS's third-party register; imported untrusted files should be handled with care.

## 11. Profiling and proof

Available features include CPU profiling, Chrome trace export, capture/replay, deterministic frame sequence capture, perceptual image comparison (LDR-FLIP/SSIM/temporal error) and `victus run --render-report` reason codes.

The render report explains whether a feature is active, reduced or off and why (quality tier, setting, scene, budget, requirements, unsupported path, capture mode, missing history, etc.). It does not provide GPU pass timing in this version.

The game should have a demo diagnostics page or overlay using only real values. If a metric is unavailable, label it unavailable. Use device-side system tracing or Android profiling tools only after verifying that the method works on this specific phone.

## 12. Known risk register

| Risk | Why it matters | Required response |
|---|---|---|
| Hot 10S Vulkan support/driver | Engine Android path requires Vulkan 1.1; actual phone is untested | Verify device capability and run a minimal exported scene immediately |
| Sustained thermal performance | Older budget SoC may throttle during dense forest rendering | 20-minute physical play test; measure performance over time |
| Virtual controls missing | A game cannot be played comfortably on touchscreen without them | Implement game-level multitouch controls and test on device |
| Ragdoll recovery gap | Current ragdoll doesn't get up or follow the gameplay root | Build a controlled recovery state machine |
| Face morph CPU cost | Detailed faces may be expensive if many update every frame | Restrict detailed morphs to speaking hero characters |
| Volumetric fog cost | Cost on Mali-G52 is unknown; fog has documented limits | Compare volumetric with cheaper distance/height fog on the handset |
| Foliage CPU overhead | Per-instance CPU culling can become a bottleneck | Use chunked, distance-limited, instanced foliage and profile |
| GPU pass timings absent | Can't directly attribute per-pass GPU cost from engine telemetry | Report as unavailable; use supported external device tools only if validated |
| Voice model rights/runtime cost | A free model can have restrictive voice data or redistributability terms | Pre-render lines, archive per-voice license and provenance |

## 13. Audit conclusion

VICTUS has enough real subsystems to make a technically meaningful 3D reference game: PBR rendering, environment lighting, skeletal animation, physics, navigation, AI, audio, UI, assets, scripting, profiling and an Android package path.

The main engineering uncertainty is **not whether the repository contains graphics and gameplay code**. It is whether the current Android path, controls, quality profile, scene complexity, audio, lifecycle and sustained frame pacing work well on the actual Hot 10S. Prove that early with a very small exported scene, then build the forest vertically on top of verified results.
